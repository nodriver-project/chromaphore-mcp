# Design notes

Why the server works the way it does. The code comments point here.

## Talking to the browser

- **The debugging pipe, not a port.** The server starts `chrome.exe` with `--remote-debugging-pipe`: commands go to the browser's file descriptor 3 and answers and events come back on 4, one JSON message per NUL-terminated line (`server/src/cdp.ts`). No local port is open for other programs to find, and there is no stderr to parse.
- **Started outside the server's process tree.** Node on Windows ties every child it starts without `detached` to itself, so the browser would die with the server however the server ends; Claude Code also kills a server's whole process tree 300 ms after closing its stdin at the end of a session. The server therefore starts the browser through a short launcher process (`server/src/launcher.ts`) that starts `chrome.exe` detached, hands it its own descriptors 3 and 4, prints the pid and exits. When the server goes, the pipe closes and the browser closes itself cleanly (Chromium's pipe handler calls `CloseBrowserSoon`): measured about 0.1 s later, profile `exit_type` Normal. On stdin close the server also stops a running recording and sends `Browser.close`. (`server/spikes/spike_shutdown.mjs`)
- **One flat session per tab, for the tab's life.** The custom commands keep per-session state (the pointer, the settle arm), and the human-timed Input commands run only on the tab's own session, never an iframe's.
- **No `Runtime.enable`.** `Runtime.evaluate` and `Runtime.callFunctionOn` work without it, and isolated worlds come from `Page.createIsolatedWorld`. On v156 enabling it showed nothing a page could see (below), but the server needs nothing from it.

## Launch switches

Always (`server/src/browser.ts`, `BASE_SWITCHES`):

- `--remote-debugging-pipe`, `--user-data-dir`, `--fingerprint-seed=<n|auto>`, `--no-startup-window`.
- `--disable-hang-monitor`: no "page unresponsive" dialog nobody can answer.
- `--auto-decline-webauthn`, `--dismiss-permission-prompts`, `--cancel-print-preview`, `--cancel-payment-request`: prompts nobody at the window can answer are closed as a person would (permissions dismissed, nothing remembered; print previews and payment sheets cancelled).
- `--private-clipboard`: the browser's own clipboard, so the machine's (the user's) is never read or overwritten; `paste` uses it.
- `--enable-canvas-text-record`: the browser records what 2D canvases draw, for `Page.agentCanvasText` (below, "Two browsers"); off by default in the browser, ignored by one that predates it. (The owner, 2026-11-17.)
- `--disable-auto-reload`: a network-error page stays as it is instead of reloading itself unseen.
- `--disable-renderer-backgrounding`, `--disable-backgrounding-occluded-windows`, `--disable-background-timer-throttling`: tabs the agent is not looking at keep running at full speed.
- `--disable-features=Prerender2,UseEcoQoSForBackgroundProcess,AvoidUnnecessaryBeforeUnloadCheckSync`: no hidden prerendered pages or extra targets under the agent; background processes off Windows' efficiency mode. (AI Mode's eligibility request to google.com at every launch, `AimEnabled`, the browser's own preset disables from Chromaphore 1.0.0 on.)
- Headless only: `--headless=new`, `--mute-audio`, `--enable-gpu`, `--fingerprint-screen=auto`, `--fingerprint-screen-position=auto` (the seed's screen; headed shows the real monitor and window, which must agree).
- Headed only: `--show-cdp-cursor`, so whoever watches the window sees the pointer the tools move. The browser draws it on a layer of its own over the page (`content/browser/devtools/cdp_cursor_overlay.h`): the page never sees it, nor does a screenshot. Added in 0.2.1, after a session found no cursor in a headed window; checked 2026-11-10 with `spike_signals.mjs --headed-only` (no check differs from a person's launch) and a screen grab with the pointer resting on a hovered button.

Never: `--enable-automation` (shows the "controlled by automated test software" bar), `--disable-ipc-flooding-protection` (a page can count `history.replaceState()` calls: Chrome lets 200 through in 10 s, the switch all of them), `--disable-renderer-accessibility` (starves the page snapshot), `--remote-debugging-port` (the pipe replaces it).

The browser itself already adds a preset on every launch (first-run, sync, telemetry and background-traffic switches, `--hide-crash-restore-bubble`), so the server does not repeat it.

## Automation signals

`server/spikes/spike_signals.mjs` loads `server/spikes/automation_probe.html` in five setups, with and without a window: a person's launch (profile and seed only), the server's switches without debugging, and the server's switches driven over the pipe, over a port, and over the pipe with `Runtime.enable`. The driven runs do what the server does (settle, a listing with a screenshot, an evaluate, two human clicks, typing). The page checks `navigator.webdriver`, the outer-minus-inner window sizes, focus and visibility, plugins, languages, `window.chrome`, notification permission against the permissions query, connection RTT, the WebGL renderer, media devices, voices, globals beyond a fresh frame's, `debugger`-statement timing, accepted `history.replaceState()` calls, and seven console-preview traps (getters on an Error's `stack` and `message`, an object, an array index, `Symbol.toStringTag`, `constructor`, and a Proxy's traps).

On Chromaphore 156 no driven run differs from a person's launch, headed or headless. Three of the traps fire in every setup alike, because the browser turns console arguments into text whether or not anything is attached. Input arrives trusted, with a curved path of 140 to 280 mouse moves before a click and 150 to 420 ms between keys.

Seen on the way, and not signals: a page's first script sees a 0x0 outer window, position 0,0 and no focus whenever it is not the tab's first page, with or without any debugging switch, in stock Chrome as here (`spike_window2.mjs`); the real values arrive within 2 s.

## Acting and settling

- An element is acted on in three steps: `Page.agentNodesAlive` then `Page.resolveAgentNode` (its node and local root frame), `Input.revealElement` (scrolled into view with the wheel), then the action (`Input.moveTo` with a click, `selectOptions`, `fillDateTime`, ...). The browser labels each listed element (`a12`): a label stays with its element for its life in the document but starts again at `a1` in every document, while `agentNodeId`s are unique across the whole browser. So the label is looked up with `agentNodesAlive`, never read as an `agentNodeId`. Up to 0.2.0 the plugin did read it so, and clicks failed in every document after the browser's first ("no longer on the page"; found on Hetzner, whose cookie banner reloads the page).
- An id the model reads is that label with the letters of its page in place of the `a`: the first page a listing shows (a tab's document, by the snapshot's `documentId`) gets `a`, the next `b`, then `c` … `z`, `aa` (`browser.ts`, `lettersFor`). The count is the Claude Code session's (`CLAUDE_CODE_SESSION_ID`, which Claude Code gives the servers it starts; one server serves a session and its subagents). It is saved under `%LOCALAPPDATA%\Chromaphore\ids\<session>.json` before the letters go out, so a browser opened after another, or a server restarted under a live session (an `/mcp` reconnect, a crash), goes on from the letters already given and an id the model still holds names no page of the new one. The file is read and written under a lock (`<session>.json.lock`, made exclusively; one older than 10 s is taken as left by a dead process), so two servers of one session hand out different letters while the lock holds, and replaced whole through a `.part` file and a rename, so a crash mid-write never leaves it empty. Only a missing file means "none yet"; unreadable content is replaced by what the server knows, so the file is right again for later servers. A count that cannot be read or saved does not fail the reply, which may come after an action that already ran: the letters go on from the process's count, and the reply says once that an id given before the plugin last restarted could name a page now. Known limit: two servers that find a crash-left lock at the same moment can both take it, and then hand out the same letters. A count untouched for 30 days is deleted when a server starts (never by the session's own server); its session's server then carries on from its own count. Without a session id the count is the process's. `s` and `t` are skipped, being the letters of snapshot and tab ids. NoDriver does the same since its `795d7ea`, counting per Longhaul conversation and keeping the count across app restarts (its session's report, 2026-11-10). A page restored from the back/forward cache keeps its `documentId`, so it gets its letters back and its old ids work again. Without them a label alone would name another element once the tab moved on: an id the model planned from one page, sent after an action that loaded another (calls sent together, or a cookie banner's reload), would act on whatever has that label on the new page, and so would an id from another tab. With them, `resolve` refuses an id whose page is another tab's (or a closed tab's, or a closed browser's), or whose document is not the one `agentNodesAlive` answers for. The settle report also names listed elements by label, from the latest listing of the document it ran in, which after a back/forward restore is not the one the tab's letters name; its lines keep the elements' names and leave the labels out. The label is taken only where the browser puts it (`settle_join.cc`, `Relabel`): at a mutation's start; for an animation, first the parenthesised shape the browser uses when its own words have no " on " (the first ` (aN "` with the words ending in `")` and standing before any " on ", or a bare ` (aN)` at the very end with no " on "), else right after the first " on " when a label follows it there. So a name holding " on ", " on a5" or " (a1)" keeps its words. NoDriver's `AgentIds.unlabelled` found the first two leaks; it tries " on " first and still leaks a parenthesised name holding " on aN" (the plugin's 0.2.3 review, 2026-11-11).
- Before an id is acted on, it gets the checks NoDriver makes (`NoDriver4j`, `bridge/session/IdCheck.java`), in the plugin's own words, from one `agentNodesAlive` read with `layers`. Two differences: the plugin checks on every call, where NoDriver checks only after the page may have changed or for an id its latest listing lacks; and a retry after a reads-changed refusal acts, a rule of the plugin's own. The plugin keeps what each listing printed of every element, by page, as what the agent was shown, and every capture refreshes each element shown before, printed or not, as NoDriver's `ListingMemory.given` does (a placeholder that changes prints no line in a reply, yet changes what the field reads as). An id is refused, with the reason, when:
  - the tab's page is loading a new document: a main-frame load started and has not committed or failed, for 30 s at most. The `navigation` events come from every command's answer and from the late `Input.actionOutcome` events, matched by `actionId`, so an end handled before the answer that told the start does not leave the page loading;
  - the element is gone;
  - it is off screen and no listing printed it;
  - it is behind a layer now, or was behind one that has closed since;
  - it is no longer listed;
  - it no longer reads as it did when the agent saw it (a button's "Save" now "Delete account"). The refusal tells what it reads now and counts as seen, so a retry acts on it.
  An element whose frame did not answer is let through; the action checks what it reaches. `server/test/id_checks.mjs` covers each. (Plugin 0.2.2, on the owner's word of 2026-11-10 that the plugin and NoDriver should handle ids the same way.) The screenshot's badges are drawn by the browser and always read `a12`; `view` says which letters they stand for on a later page.
- The server keeps a copy of the pointer per tab from every answer and sends it with every pointer command; a tab's first command sends the view's centre. "The pointer is outside the page's view" moves it to the centre and retries once; a landing that was covered is re-aimed once.
- Every action ends with `Page.agentSettle` on the action's own id, then a listing with `since` the tab's previous one, so the answer says what changed. "Not the current action" settles again without the id.
- For a moment after a commit, Page commands answer "Not attached to an active page" until the session has moved to the new document; the server retries them for up to 3 s.
- A JavaScript dialog blocks the page: an action that opens one answers at once with its text instead of waiting on a page that cannot answer.
- Typing: 60 to 260 ms between keys, a thinking pause now and then, a rare typo corrected at once, never in passwords, numbers, codes or card fields; `exact` turns typos off.
- **Points (0.3.0).** `click`, `hover` and `drag` also take a point of the view in CSS pixels, for text an editor draws itself: Google Docs draws each page on one `<canvas>`, with no element for a line or a word, and sets `pointer-events: none` on it, so an element click is refused there ("the hand could not get onto it"). A point of a click or a hover goes to `Input.moveTo` as `x`, `y` with no hit check: whatever is at the point takes the press, as with a hand. A point outside the view is refused before anything moves; nothing scrolls first. Measured in Docs (2026-11-16, release 156.0.8078.47): a click at a character boundary puts the caret exactly there, and a drag between two points over a word, with the browser's own drag (below), answered "pointer drag, released" and selected that word (typing then replaced it).
- **Points off a scaled image.** The browser shrinks a large view's screenshot to about 1,125,000 pixels and says by how much (`viewport.screenshotScale`, image pixels per CSS pixel). Each kept image keeps its scale, the view size and its tab; `view` says when the scale is not 1 (a 1920x945 headless view, fingerprint seed 1, gives 0.787). `click`, `hover` and `drag` take `snapshot_id` with a point read off the image: its pixels are divided by the scale. A snapshot of another tab, or of a page the tab has left (the image's letters are not the tab's), is refused.
- **A drag from a point is the browser's own drag.** It is `Input.performDrag` with `grabX`, `grabY` in place of an element, the target as `pointX`, `pointY` or an element, `modifiers`, and the pointer, as the drag of an element. The browser presses, carries, lets go and answers once; a drag that fails is ended by the browser itself (a pointer drag let go where it was grabbed, a native one called off), so no tool sends a press without its release in the same command, and the server keeps no state about a button. The answer says what the page made of it, in the element drag's words: "Dragged from (x, y) to (x, y) (pointer drag, released)" selects text; a native drag (dropped) means the press landed on something the page drags itself, in an editor text already selected, and that text was dragged, so the answer says so plainly. Any other outcome is told with its reason and whether the button came up where it went down. Measured on a local contenteditable (2026-11-16, release 156.0.8078.47, headless): between two boundaries it selects exactly the text between, on one line and across two, with one mousedown and one mouseup; Shift reaches the press and extends the selection; a press on selected text answers `native`, `dropped` and moves the text; an element below the view is reached, the browser turning the wheel under the carry (scrollY 0 to about 2000, the mouseup on the element), so a drag to an element needs no check of its placement; a target removed on the press answers `gone` and the page sees the mouseup at the press point, and the next click goes through. Without `pointerX`, `pointerY` on a tab whose pointer the browser does not know it answers `unreachable` ("the pointer's place is not known"), so they always go with it. A drag between two points inside a frame of another site is refused by the browser (measured 2026-11-17 on a local page framing another site: `covered`, "div#ed in another frame is on top of where the element to grab would be grabbed"), though a click at the same point works; the answer adds that the start point is in such a frame. The hint goes only with that wording of the reason, since a covered target is also told with "in another frame". A drag from a point to an element inside the same frame was not measured. (`test/points_and_bursts.mjs`, `test/focus_cancel_fetch.mjs`.)
- **Bursts (0.3.0; on a browser of release 2.0.0 or older, a newer one plays the burst as one command, below).** `type` with `keys` plays a scripted burst: strings through `Input.dispatchKeystrokes` with no typos of its own (each with the seed plus its index), `{"bs": n}` as n Backspace chords at 1.6 times the pace (a chord's own timing put them 240 to 270 ms apart, a person's are 100 to 200; with it, 170 to 220), `{"pause_ms": n}`, and `{"press": "Ctrl+I"}` as a chord. Between steps the server waits 40 to 160 ms (divided by the pace, drawn from the seed) on top of the lead the browser gives each press. The whole seed (up to 2^47) is mixed into the generator's state, so small and neighbouring seeds give unrelated gaps; before, seed 1 pinned the first gaps at 40 and 42 ms. Only the last step, when it is a string, asks the browser to read the field back: the read adds the browser's 150 to 450 ms field settle to each call that asks for it. A seed fixes the rhythm of the typed strings only (measured 2026-11-16: the same text and seed gave the same gaps between keydowns to the millisecond, another seed gaps up to 150 ms apart); the browser times chords, Backspaces and shortcuts afresh each call. `speed` is `speedMultiplier` against the browser's typist (drawn from the persona seed); the browser stops at about 110 words a minute. The time a burst will take is not known before it runs until the browser can plan a schedule without sending it (the browser brief, BR2). `seed` needs the replay options setting (below); without it each call draws its own.
  - Before anything is sent, every `press` is parsed and its key checked against the keys the browser's chords take: a named key (Enter, Space, ArrowDown, F5...) or one printable ASCII character, `!` to `~` (`BuildKeyMapping` in `keyboard_typing_session.cc`; `Ctrl+ö` would fail midway). So a step the browser's chord cannot press fails with nothing sent. A step that fails once keys have gone out (a CDP error) stops the burst: the answer names the step and why, counts what went out before it, and then settles and lists the changes as usual; nothing after it goes out, `submit` included. If the settle or the listing then fails too (the browser died mid-burst), the answer is the account with a line saying the page could not be listed afterwards and why.
  - *Needs the replay options setting.* With `text`, the burst must leave exactly it, checked before anything is sent: strings, less what Backspaces take, with a plain `{"press": "Enter"}` as "\n", `Tab` as "\t", `Space` as " " and `Backspace` as one `bs`. A "\t" inside a string is a real Tab too (measured 2026-11-16: the focus moved to the next field), and "\n" is Enter; "\b" is not Backspace. Any other press without Ctrl, Alt or Meta, and a Ctrl or Meta chord on a, v, x, z, y, Backspace, Delete, Enter, an arrow, Home or End, is refused with `text`, since the check cannot follow what it does; other chords (a formatting toggle) are trusted to leave the text alone. A Backspace that would reach before the burst's start is refused with `text`, since `text` cannot show what it deletes. Without the setting, `text` and `keys` together are refused before anything is sent. Without `text` any press is played; the answer says what the burst leaves only when it has no press of the refused kinds, and says when its Backspaces reach back before its start.
- **Cancellation** (on a browser of release 2.0.0 or older; a newer one stops the keys under way, see "The focus check and the burst through the browser"). A cancelled request (the MCP request's `AbortSignal`) stops sending input: the wait for `not_before`, a burst's pauses and the gaps between its steps end at once; the signal is checked before every step and every Backspace of a run; after it nothing more goes out, `submit`'s Enter included. The SDK drops a cancelled request's answer, so the server returns at once without a settle. A string being typed when the cancel comes runs to its end: a new typing, chord or paste call would cancel it in the browser (`active_typing_session_.reset()`), and a no-key `dispatchKeyChord {modifiers: 0, phase: "up"}` does stop it at once, but the stopped call answers "Typing session aborted" and the keys it had down stay down: measured 2026-11-16, the page saw a letter's keydown with no keyup every time, and a Shift keydown with no keyup in 2 of 8 runs. So it is not sent.
- **`not_before` (0.3.0; needs the replay options setting).** `type`, `press` and `paste` wait for an absolute time (ISO 8601 with its zone, or epoch ms; at most 15 minutes ahead) before the first key or paste, so a caller keeping to a schedule is not at the mercy of its own turn's latency. Everything that can be refused is refused before anything moves: the time (one more than 15 minutes ahead), the burst's steps and text check, and the `expect_focus` id. Then the click into `id` (placement, not a change), then the wait, then the dialog and focus checks. The `expect_focus` id is resolved again after the wait, right before the focus check: the wait can last 15 minutes, and its element may have gone meanwhile. A timer can fire a millisecond or two early, so the clock is read again and the wait goes on until it is past the time. The answer says when the input ran, from just before the first command went out to its answer (which comes once the last key is up).
- **`expect_focus` (0.3.0).** `type`, `press` and `paste` send nothing unless the given element has the keyboard focus, checked once, right before the first key. What follows is the check on a browser of release 2.0.0 or older; a newer browser reads the focus itself (below, "The focus check and the burst through the browser"). Found in Docs on 2026-11-16: selecting text opened a Gemini prompt box that took the focus, and the next 70 characters went into that box. The check runs in an isolated world the page cannot see, on the element itself (`DOM.resolveNode` into the world, then `Runtime.callFunctionOn`): from `document.activeElement` through open shadow roots and into same-origin frames (Docs takes keys in an editable inside a same-origin frame). A frame whose `<body>` has the focus and is editable (contenteditable, or `designMode` on) is an editor: the body has the focus, and an id naming the frame element counts too. The world is asked for again before each check: `Page.createIsolatedWorld` with a `worldName` gives the same world again while the document lives (`dom_wrapper_world.cc`, `EnsureInspectorIsolatedWorldWithName`), so no context id is kept, which could name another context once a new renderer process starts its ids again. A closed shadow root cannot be entered from script: the innermost element reached is then its host, so a refusal because another element has the focus names that element (its tag, role, `aria-label` and id), which shows such a case. An element in a frame of another process cannot be checked from the page: `expect_focus` on it is refused before anything moves, and leaving it out sends the keys unchecked. An element in a frame of another origin in the same process (a `data:` frame, measured 2026-11-16; a sandboxed frame ran in another process) cannot be read either: `DOM.resolveNode` gives the check's world no object for it (`resolve_node.cc`), so the refusal says the check cannot read the frame the element is in, not what has the focus, with the same way out.
- **`quiet` (0.3.0).** An action's answer leaves out the `+`, `-` and `~` lines and counts them, keeping what opened or closed on top, the focus, URL, title, scroll and announcements. In Docs every key changes much of the listing. Seen 2026-11-16: an action right after an `observe` with `offscreen: "full"` gets no change listing against it (the browser answers that the listing is not comparable), quiet or not.
- **`fetch` with `save_to`.** The browser saves a binary body to `saveTo` and replaces a file already there; it returns a text body under 8 MiB as text and saves nothing (both measured 2026-11-16), and a text body past 8 MiB it writes to the file whole, the answer keeping the head. So before the request goes out the server refuses a `save_to` that exists and makes its folder; a folder that cannot be made is refused, and nothing is sent (a POST must not run and then lose its answer). After the request the server writes a body the browser returned as text itself (made new, never replacing), and the answer says what it saved: the response's text, or for an HTML page the Markdown it was rendered to (`mode: "raw"` saves the HTML as it came); a body the browser cut short (`truncated`) is said not to be the whole of it. A failure to write is a line of the answer, which still carries the response as it would without `save_to`; when nothing was saved, the answer says so. Known limit: a file made between the server's look and the browser's write is still replaced.

## Two browsers (0.4.0)

The browser gained commands after release 2.0.0 (the browser's own brief, parts BR1 to BR4, built in the build tree on 2026-11-17 and in no release yet): `Page.agentCanvasText`, `Input.readFocusedField`, `Input.dispatchKeystrokes` with `steps`, `stopWhenFocusLeaves` and `expectField`, `Input.readClipboard` and `Input.writeClipboard`, and `performDrag`'s `buttonDown`. The plugin works with both kinds of browser: on an older one every feature below falls back to the 0.3.0 behaviour where there is one, and is refused with one sentence where there is none ("This browser predates aiming by text: it needs a Chromaphore build newer than release 2.0.0. Nothing was done.").

- **The probe.** Both browsers report version 156.0.8078.47, so the version cannot tell them apart. When the first tab opens, the server sends `Input.readFocusedField` on its session, once per browser (`browser.ts`, `probeModern`). An older browser answers code -32601 with `'Input.readFocusedField' wasn't found`, as it does for any unknown method (measured 2026-11-17 on the installed 1.0.0 release: `readFocusedField`, `readClipboard`, `agentCanvasText` and a made-up method all answered so). That answer, and only it, marks the browser as older; any other answer, an error included, means the command is there.
- `--enable-canvas-text-record` is always passed: recording is off in the browser by default and only draws made while it is on are recorded, so it must be on from the launch. An older browser ignores it. (The owner, 2026-11-17.)
- The tests take the browser from `CHROMAPHORE_TEST_BROWSER`, passed to the server as `CHROMAPHORE_BROWSER`; without it, the installed release. A test of a feature of the newer browser, run on an older one, checks the refusal or fallback there and prints one `SKIP` line for the rest.

The rest of this design is the lead's (2026-11-17).

## Canvas text (0.4.0)

`Page.agentCanvasText {inView: true}` answers the text runs and filled rectangles each 2D canvas still shows, with every point in the space `Input.moveTo` takes (`server/src/canvas.ts`).

- **Lines.** Only 2D canvases' runs are read. Format characters (U+202A to U+202E, U+2066 to U+2069, U+200E, U+200F) are dropped from the text shown and matched; each run keeps the map from a cleaned index to the raw boundary, since `advances` has one entry per UTF-16 boundary of the raw text. Runs whose baselines lie within half the smaller box height of each other (ascent plus descent, from the run's quad) form a line, ordered by x. Two neighbours with a gap wider than 0.15 of the smaller box height are joined by one space: Google Docs does not draw whitespace at a run's ends, so "test. **Plain**" arrives as "test." and "Plain" with a gap. Runs with no gap are joined directly ("italics" then "."). A rotated run is a line of its own. Lines are read top to bottom within a canvas, canvases in the answer's order.
- **What the lines cannot know:** how many spaces a gap stands for (always one), a tab (a wider gap, still one space), whether the next line is a wrap or a new paragraph, and columns (runs of two columns on one baseline make one line).
- **In `observe` and after `navigate`** the listing ends with "Canvas text in view:" and the lines, indented, up to about 6,000 characters, then "… N more lines". When runs in the lines are not exact, one line says so with the reasons present (`partlyCovered`, `notFollowed`, `fontChanged`); a truncated canvas, `runsCut` and `framesLeftOut` get a line each. The exactness line is judged on the runs only, not on `canvas.exact`: a page that clears a band to redraw a line (as Docs does) cuts into its own white background fill, which makes that fill and so the whole canvas inexact while every run stays exact (measured on the test page).
- **After an action** (plain or `quiet`), when the page showed canvas text at the tab's last read, the answer ends with what changed: removed lines with `-`, new ones with `+`, compared as text, so a line that only moved, or one redrawn with its neighbours, is no change. More than 12 changed lines (a scroll) become one line: how many lines show now, the first and the last. No change prints nothing. The tab remembers the lines of its last read with the page's letters; a page with no canvas text at its last read costs no read after an action, and an answer that is a whole listing (a new page) ends with the whole section instead.
- On an older browser none of this happens, and nothing says so: the listing is as in 0.3.0.
- **Measured on a page drawing as Docs does** (`test/canvas_text.mjs`, 2026-11-17): each string in U+202D … U+202C, formats as runs of their own, a changed line redrawn by clearing its band, clipping and drawing the neighbours again, a selection as a translucent `fillRect`. The lines read as written; the redraw answered one `-` and one `+` line; the selection changed no line; a scroll of 400 px answered the summary (40 lines). A read of the lead's Docs probe showed runs per format with a 4.1 px gap at a 16 px box, so 0.26 of the height, joined by a space.

## Aiming by text (0.4.0)

`click` and `hover` take `text_before` and `text_after` (at least one) in place of an id or a point; `drag` takes `select` with optional `text_before` and `text_after` and drags from the start of that text to its end, through the drag from a point. Given with an id or a point they are refused, as an id with a point is. On an older browser they are refused in one sentence.

- **Matching.** The flow is the lines' text, with one space where two runs were joined and one between a line and the next; every run of whitespace, in the flow and in the caller's text (spaces, tabs, line breaks, no-break spaces), counts as one space. The text must read so in exactly one place, else nothing moves and the refusal says how many places read so and what to do (scroll it into view; give more text around it).
- **The place.** A boundary inside a run is that run's boundary. A boundary on a joined space or a line's end is the end of the run before it when the caller's text puts the space after the place ("Plain" then " “quotes”"), and the start of the run after it when the space is before the place ("Plain " then "“quotes”"). The point is the boundary's point along the run (`start + (end - start) * advances[i] / width`), at the middle of the run's box in height, taken from the quad, so a rotated run works the same way. It must lie inside the canvas's `shownRect` and the view, else the refusal says to scroll.
- **Exactness.** A place in a run that reads `fontChanged` is refused, since its boundaries are estimates; `partlyCovered` or `notFollowed` adds one cautioning line and still acts.
- The answer names the place by its text: `Clicked between "Plain " and "“quotes”" at (110, 84.5).`
- **Measured** (`test/canvas_text.mjs`): every click landed within half a pixel of the boundary the page computes with `measureText`, at the middle of the font's box: at a gap both ways, at a line's end both ways, between two glued runs, and inside a run. The page saw whole pixels (110.02 arrived as 110, 105.58 as 106, a .5 either way), so half a pixel is the bound.

## The clipboard (0.4.0)

`clipboard` reads the browser's own clipboard (`Input.readClipboard`), shared by all its tabs: the text with line breaks shown as `\n` whatever the browser stored (it stores CRLF on Windows for its own pastes, `writeClipboard` and a page's copy of a selection), its length counted that way, and whether HTML is there; `html: true` adds the HTML, cut at 20,000 characters. With `set`, it first puts the text there without pasting (`Input.writeClipboard`); Ctrl+V then pastes it. The machine's clipboard is never touched (`--private-clipboard`). It can write, so it has no `readOnlyHint`. On an older browser it is refused in one sentence. Measured: after a page's copy of two lines the text read "First line\nSecond line" with 925 characters of HTML; a `set` of two lines read back the same, and Ctrl+V pasted it.

## The focus check and the burst through the browser (0.4.0)

On a newer browser `expect_focus` uses the browser's own reading (`Input.readFocusedField`) instead of the script in an isolated world (`actions.ts`, `browserFocus`).

- `press` and `paste` read the focused field before the first key and compare it with the element. `type` does the same, then passes the field to `Input.dispatchKeystrokes` as `expectField` with `stopWhenFocusLeaves`: the browser refuses before the first key unless the field has the focus, and stops when the focus leaves it. A stopped call is told: how many steps went out whole, what reached a field of the step under way (below, "The account of a stop"), the keys that may have reached the field that took the focus (`uncertainKeys`, or that none was on its way), and, when not zero, how often the focus came back and how much later the rest ran (`focusResumes`, `slippedMs`). Nothing goes out after a stop, `submit`'s Enter included.
- **The field's frame.** `Page.resolveAgentNode` names an element's local root; `readFocusedField` names the field's own frame, and `expectField` compares with that: given the local root for a field in a same-process frame it refused that very node (measured: "the focus is on backendNodeId 37 in frame BD73…, not on the field expected"). So the server matches the backend node id and checks that the reading's frame is one of the element's local root's renderer (the local root itself, or a frame in that session's `Page.getFrameTree`, which lists exactly the frames of the same process), then passes the reading's own frame as `expectField`. A backend node id is one renderer's: two fields in two processes can both be id 1 (measured), so the frame check is needed.
- **Naming what has the focus.** The refusal describes the focused node with `DOM.describeNode` in the 0.3.0 words (tag, `role=`, `aria-label`, `#id`), on the session of the renderer that holds it: the tab's for its own frames, else a session attached to the frame's own target for the call. Described on the tab's session, a node of a frame of another site named the main document instead (measured), so the session is chosen by the reading's frame.
- **Measured on the newer browser, each case** (2026-11-17, `fields` probes and `test/focus_cancel_fetch.mjs`): a main-document input, an input in an open shadow root and one in a closed shadow root all read as that input and pass; a field in a same-process frame (`srcdoc`, and a `data:` frame) reads with its own frame id, passes with that frame given; a field in a frame of another site (127.0.0.1 framing localhost) and one in a sandboxed `srcdoc` frame (another process) read with their frame's target id and pass. So the 0.3.0 refusals for a closed shadow root (naming the host) and for a frame of another site or origin become real checks: the keys go through when the field has the focus, and a refusal names the field inside. A focused editable `<body>` of a frame (`contenteditable` body, `designMode`) reads as `kind: "none"`, and a burst with `stopWhenFocusLeaves` there is refused ("the focus is on no element"); for that case the server runs the 0.3.0 script check, which knows such a body, and sends the keys unwatched. Google Docs' editable is a `contenteditable` div in a same-origin frame (kind `editable` in the lead's probe), so it is watched.
- **A burst as one command.** `type` with `keys` is one `Input.dispatchKeystrokes` call with `steps`: strings as `{text}`, `{"bs": n}` as `{backspaces: n}`, `{"pause_ms": n}` as `{pauseMs: n}`, `{"press": …}` as `{chord: {modifiers, key}}`, with the strings' pace parameters, no typos, and the seed when one is given. The plugin's gaps between steps, its faster Backspace pace and its per-step seeds are not used: the browser times the whole burst on one schedule, and the answer says "one schedule" with its planned length. The checks before anything is sent stay as they are. `clear` and `submit` stay separate chords. Measured: the page saw the keys in order, a 900 ms `pause_ms` stood 1,008 ms between two keydowns (the browser counts from the keyup, rounded to its 8 ms reports).
- **Cancellation.** A cancelled request now stops a string or a burst under way: the server sends `Input.dispatchKeyChord {modifiers: 0, phase: "up"}`, which replaces the typing session and lets its keys come up first. Measured on a page logging keydown and keyup by `code`: a string with capitals cut after 1.5 s stopped at once (3 of 53 characters) with every key that went down up again, in contrast to 0.3.0's measurement below. (A log by `key` shows a false pair, `S` down and `s` up, when Shift comes up before its letter.)
- On an older browser all of this is the 0.3.0 code, unchanged: the script check, the burst as separate calls, and a string under way that runs to its end when cancelled.

## The account of a stop (0.4.0)

The browser's `charsSent` counts the characters of the step under way whose keys all went out, up as well as down. A key that is down but not yet up has already typed its character, so the count fell short: in the lead's runs (2026-11-17) the field held six characters ("A stri") while the answer said "after 4 of 42 character(s)". So with `expect_focus` on a newer browser `type` asks for the timeline (`timeline: true`) and counts from it: the characters of the step under way whose own key went down (a Shift's events carry the character it went down for and are not counted, nor a typo's) reached a field, the watched one or the one that took the focus; those whose keydown the browser lists in `uncertainKeys` may have gone to the latter. The answer says both, for a string ("after 6 of 42 character(s) had their key go down (they reached a field)", then "Of them, the browser lists 1 as uncertain ("i"): … so a2 holds between 5 and 6 of them") and for a burst's step under way (its Backspaces, for a `bs` step). A stop inside a typo says a wrong character may stand in the field. Without a timeline (it is always asked for here) the answer falls back to `charsSent`.

Measured with `test/browser_input.mjs`, whose page moves the focus once six characters have landed (the lead's change; it was 600 ms after the first key, which a thinking pause could outlast): in three runs on the newer browser the first field held 6 characters each time, and the answers said 6 went down, with the sixth listed as uncertain in five of the six stops (the browser hears of the focus change only after the page handled that character's input). The check is that the field holds between the characters that went down less the uncertain ones and all that went down.

## Editor modules (0.4.0)

The canvas text shows what an editor that draws its own text shows, but not where the caret is or what is selected; that takes facts true of one editor only. So each editor has a module of its own (`server/src/editors/`), and nothing of it is in the general tools: the listing code asks the registry (`editors/index.ts`, `editorLines`) whether a module knows the page and what it says, with the canvas read it already made and a way to run one script in an isolated world of the main document. Only a page whose canvas read holds a 2D canvas is asked about. The lines go at the end of `observe` and `navigate` answers and of every action's answer, plain or quiet, after the canvas text and its changes. A page a module knows is read after every action even when it shows no canvas text (an empty document). On an older browser, or a page no module knows, nothing is added.

**Google Docs** (`editors/docs.ts`). Built on the lead's measurements on a real document with the newer browser (2026-11-17):
- The pages are canvases of class `kix-canvas-tile-content`. That class in the main document is the signature; the address is not looked at.
- The caret is a DOM element, `#kix-current-user-cursor-caret`, inside an element of class `kix-cursor`, which has `display: none` while a selection exists. Its left edge sits at a run's boundary within half a pixel, and its box spans the line: caret at x 321, top 180, height 16.9; the boundary after "Chr" at 320.6; the run's box from y 180.8 to 196.8. The caret stays drawn, no longer blinking, when the keyboard focus goes elsewhere (the title box): with the document focused the page's active element is the frame that takes its keys, an iframe of class `docs-texteventtarget-iframe`, so the module reads that too, and a caret drawn while that frame is not the active element is told with "The document does not have the keyboard focus: keys would not go there." (found on the real document, 2026-11-17: the first build said the caret's place as if the keys would go there). A page with no such frame gets no such note.
- A selection is `fillRect`s in `Page.agentCanvasText`'s `fills`, of colour exactly `rgba(78, 143, 248, 0.5)` while the document has the focus and `rgba(143, 143, 143, 0.34)` while it does not: one per line, the left and right edges at run boundaries, reaching one space's width past the line's last run when the line's end is selected (a fill from 297.0 to 978.6 where the last run ended at 974.5; the space is 4.1 wide at that size).

The module reads the signature and the caret's box (`getBoundingClientRect`, whether any ancestor has `display: none`, and the view's size) in one evaluation in the isolated world the focus check uses. Then:
- **The caret**: the boundary nearest its left edge among the lines its box overlaps by more than half, if within 2 px, told as `Docs caret: after "…" and before "…".` with up to 40 characters of the lines' text each side (the lines joined by a space, as in part A's flow, so a neighbouring line's text may follow), and `(at the start of a line)` or `(at the end of a line)`. A gap between two runs has two boundaries 4 px or so apart, the end of the run before and the start of the run after, so the caret before and after a space read differently. A caret on no line with text is on an empty line: told with its place and the text of the lines around it. A caret above or below the view is said to be out of view.
- **The selection**: each fill of either colour (its `color` string read as rgba, times its `alpha`, which is the global alpha it was drawn with: measured 2026-11-17, a fill of `rgba(78, 143, 248, 0.5)` answers that string with alpha 1, a `#4e8ff8` at global alpha 0.5 answers `#4e8ff8` with alpha 0.5) belongs to the line its box overlaps most; its edges go to the nearest boundaries, and an edge more than 0.15 of the last run's height past the line's last run takes the line's end. A fill on no line with text is an empty line's break. The lines' texts, top to bottom, joined with `\n`, are quoted with their count, and a second sentence names the lines whose end is selected too; grey fills add that the document does not have the focus.
- **Neither**: one line says so (the document lacks the keyboard focus, or they are out of view).
- **What it cannot know**: the text as drawn cannot tell a wrap from a paragraph break or count the spaces in a gap (always one), so the skill says to copy (Ctrl+C) and read `clipboard` for the exact selected text. The caret's box is in CSS pixels of the view; at a page zoom other than 100% it and the canvas points may disagree (not measured).

Measured on a local page that imitates the signature (`test/docs_editor.mjs`, 2026-11-17, newer browser): the caret placed at boundaries the page computes with `measureText` read as expected inside a run, on both sides of a joined space, at a line's start and end, at the end of the last line and on an empty line; selections inside one line, across two lines with the first one's end, to a line's end and stopping at its last run, from a run's end over a joined space, focused and grey, read as drawn; neither read so; a plain and a quiet action ended with the caret line; the same canvas and caret without the class gave no line. The lead runs the real document.

## The drag's answer (0.4.0)

When `Input.performDrag` answers `buttonDown: true` (its own button still down), the server lets go with `Input.moveTo` and a release end where the pointer is, and the answer says so. It could not be provoked honestly on a local page (the browser answers it when an Escape is still on its way or its release could not be delivered), so it has no test. On the newer browser a drag between two points inside a frame of another site is carried out in that frame: measured on 127.0.0.1 framing localhost, "Dragged from (76.7, 114.7) to (191.2, 114.7) (pointer drag, released)", and the frame selected exactly "bravo charlie", between the two boundaries. ## General and replay options

A feature is general when an agent can use it from what the page shows and what it decides itself; it is a replay option when it needs a value only a caller's own pipeline produces. Three are replay options: `not_before` on `type`, `press` and `paste` (with the "Ran from … to …" line it adds), `seed` on `type`, and `type` with both `text` and `keys`, where `text` is what the burst must leave. 0.4.0 adds `dry_run` and `key_log` on `type` (below, "Replay additions"). Other people use this plugin, and their agents should not be shown options that need a pipeline of the caller's own. So the three sit behind one plugin setting, `replay_options` ("Replay options", a boolean, off by default), passed to the server as `CHROMAPHORE_REPLAY_OPTIONS`. (The owner, 2026-11-16, on the lead's recommendation.)

Claude Code substitutes a boolean option into an env value as `"true"` or `"false"`, and fills an option never saved from its `default` (read from Claude Code 2.1.325). The server reads `true` or `1` as on; anything else, including an empty or unsubstituted value (the literal `${user_config.replay_options}`), is off. With it off, `not_before` and `seed` are not in the tools' schemas or descriptions, the server's instructions do not name them, `type`'s `text` says to give text or keys, and no skill names them. The MCP SDK's object for a raw shape strips keys it does not list, so a `not_before` an agent sent anyway would vanish and the keys go out at once. With the setting off, `type`, `press` and `paste` therefore take a loose object (its JSON schema adds only `additionalProperties: {}`), the unlisted keys reach the handler, and a call carrying `not_before` or `seed` is refused, naming the setting, before anything is sent; so is `type` with both `text` and `keys`. The code of the three options stays, reached only with the setting on. `test/replay_options.mjs` checks both settings.

How to use the three options is a paragraph of the server's instructions, sent only with the setting on, not a skill. A skill's name and description are listed to every agent whether the setting is on or not, so a skill for them told every agent about options it could not use; the instructions are sent when the server starts, so with the setting off nothing an agent is shown names the three options. (The owner, 2026-11-16, after the third review pointed it out; a build of 0.3.0 before its release had them in a skill, `chromaphore:replay`.)

### Replay additions (0.4.0, a newer browser)

Two more options on `type`, behind the same setting and refused by name with it off (they are in no schema, description or instruction then), and refused in one sentence on an older browser:
- **`dry_run`** plans the text or burst with `Input.dispatchKeystrokes {dryRun: true}` and sends nothing; the browser leaves a session under way alone. The answer says how long the plan takes from its first key down to its last key up (and the plan's whole length when a pause leads or trails), how many key events and typos it has, the seed used and whether typos were allowed, and that passing that seed back gives that schedule. The browser plans "the field read as it would be", so the typo decision follows the focused field. It moves nothing and waits for nothing, so `id`, `clear`, `submit`, `not_before` and `expect_focus` are refused with it, by name; the text check of `text` with `keys` still applies. Measured (`test/replay_options.mjs`): a burst typed with the seed a `dry_run` answered gave the same key events as the plan, every one within 20 ms of its planned time (the browser's brief measured the length within 0.01 ms).
- **`key_log`** names a file each call appends one JSON line to: `start` (ISO) and `startEpochMs` (time zero), `seed`, `durationMs`, `typosAllowed`, `typos` (corrected), `stopped` when it was, and `events`, the timeline as the browser gives it (`timeline: true`; with `dry_run`, the plan, marked `dryRun: true`, with no start). Its folder is made if missing. A failure to write is a line of the answer, which keeps everything else; the answer says how many events went to which file. Only the typing call's keys are logged, not `clear`'s or `submit`'s chords.
- **Exact times.** With `not_before` or `key_log` on a newer browser, the time line comes from the timeline: `Ran from <first keydown> (the first key down, N ms after not_before) to <last keyup> (the last key up), M ms.`, stamped by the browser as each key was sent (`startEpochMs` plus `timeMs`). Measured: the page's own clock saw the first key within 50 ms of the time said. An older browser keeps the 0.3.0 line (from before the first command to its answer).
- **The seed used** is said whenever the setting is on and the browser answered one (`Seed N (typos allowed): pass it back as seed …`): with the setting on, every typing call on a newer browser asks for the timeline, so the browser answers the seed, drawn when none was given (measured: time-derived values near 4.7e10, inside the schema's 2^47).

The design of these four is the lead's brief (2026-11-17); the wording and the checks are the builder's.

`fetch` keeps its `readOnlyHint`, though it can send a POST and, with `save_to`, write a file where the caller names: it is a useful tool for agents, and one is unlikely to use that by accident or to do harm (the owner, 2026-11-16, after two reviews proposed dropping the hint).

## Profiles

A new profile is a folder under `%LOCALAPPDATA%\Chromaphore\profiles\`, not in Claude Code's plugin data folder, which is deleted with the plugin; profiles hold logins. A profile in use by another running browser is refused (its `lockfile` cannot be removed).

A temporary profile (`profile: "temp"`) is a folder under `%LOCALAPPDATA%\Chromaphore\temp\`. The server cannot delete it itself: the profile is locked until the browser exits, and the browser outlives the server at the end of a session. So the launcher starts a second detached copy of itself, outside the server's tree like the browser, that waits for the browser's process to exit, however it ends (`browser_close`, the session ending, the user closing the window, a crash), then deletes the folder, retrying for a minute while the browser's helper processes let go of their files. It deletes nothing outside that folder. A temporary profile left behind when the machine went down with the browser open is deleted by the next `"temp"` launch, once it has been untouched for an hour and is not in use.

Before 0.2.0 the plugin was named `chromeleon` and kept the same layout under `%LOCALAPPDATA%\Chromeleon\`. Each start of the server moves that folder's contents to the new one, each piece on its own, so whatever a browser has open moves at a later start:
- The installed release, by renaming its folder. A running browser keeps files of its release open, so Windows refuses that rename (EBUSY) while one runs from the folder (measured 2026-11-09 with a headless browser of the release; a program that keeps none of its folder's files open, such as a copied `ping.exe`, does not stop a rename). A release in use therefore stays, and its old install record is read meanwhile. Once moved, the old record is rewritten to point at the new place, for a server of the old plugin still running in another session; it stays until `browser_install` installs a newer release, so until then the old folder holds that one file. A start that finds the folder moved but no record for it (a write that failed) writes the record.
- Each profile, when its `lockfile` can be removed and the folder has not changed for ten minutes: a browser starting on it has not taken its `lockfile` yet, and moving the folder then would leave that browser a new, empty profile at the old path. `browser_open` of the new plugin maps an old profile path to the moved folder; a server of the old plugin still running gets "No profile folder" for it.

The old folder is removed once it is empty.

A release that `browser_install` replaces is renamed first and deleted only once that worked: deleting it outright would remove the files a running browser has not opened yet and break it, here or in another session. One that cannot be renamed, because a browser still runs from it or another program holds the folder, goes on a list (`%LOCALAPPDATA%\Chromaphore\remove.json`, release folders of the plugin's own only) and is deleted at a later start. `browser_install` reads the install record again after the download, so it replaces the release where it is by then, even if another session's server moved it meanwhile.
